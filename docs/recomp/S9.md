# S9: the fast loop, and the order of the work to a native 60 fps

Goal (the Host's North Star): Sheep Dog 'n' Wolf at a real, locked 60 fps on a PSP, the game's
code native and as little of the PS1 hardware emulated as possible.

Where S8c left it, in level 1 at PAL60 (PPSSPP, runtime at 99-100% of PS1 speed):

- the game draws 55-56 frames a second: its logic does not fit a 1/60 s PS1 frame;
- per second the host spends ~120 ms on timer reads (76,868 of them), ~110 ms on GPU DMA (the
  GPU packets parsed and turned into GE commands), ~110 ms on the SPU, ~113 ms in device
  updates, and sleeps ~80 ms.

The CPU is native; the GPU, SPU, timers and disc are still hardware emulated. The work left is
there.

## 1. The fast loop

A measurement used to cost a boot, the logos and the menus: about four minutes to reach the
level, for each change. Now:

### Snapshots (`snap.c`)

- L+R+START (the game does not see the three buttons, so a pad script can press them) asks for a
  snapshot. `native.c` takes it at its next host call of the top-level translated code, when no
  guest call of the BIOS is in progress. The host stack then holds nothing of the guest, so the
  machine is:
  - the `Psx` structure;
  - PS1 RAM, the scratchpad, VRAM (the GE's pixels read back first), SPU RAM and the MDEC input;
  - the translation context (guest registers and GTE);
  - the image states, the GRET stack and the dispatch table.
- Host return addresses in guest RAM stay valid: each executable's code goes back to its fixed
  host address.
- At start, `psxrt.snap` beside the EBOOT is loaded instead of booting the disc:
  1. the core's pointers stay this run's;
  2. the resident executables' code is read again from DATA.PSAR;
  3. VRAM is sent to the GE;
  4. translated code is entered at the saved host address.
- A snapshot is refused (the disc boots, the log says why) when it was made by another EBOOT (the
  disc ID and a hash of the code directory) or by a runtime with other structure sizes.
- About 6 MB, uncompressed.
- It survives every runtime rebuild that leaves the core's structures alone, unlike PPSSPP's
  save states, which hold the old PRX.
- The same mechanism can become the player's save states later.

### Bench mode

`psxrt.bench` beside the EBOOT (seconds) measures that many seconds after a 2 s warm-up, then
writes one line and stops:

```
-- bench 20 s at frame N: speed S% vbl V fps F.f | ms/s interp .. io .. (draw .. spu .. timer ..) dma2 .. update .. present .. sleep ..
```

`scripts/cycle_native.ps1` (outside the repo) runs it as `-Snap level1.snap -Bench 20`. A
waiting loop on the log catches the line, so nobody watches the run. The convert step takes about
3 s.

### Orchestra

Read-only research runs in parallel agents while the runtime is built here:

- the timer polling loop (sites, exit conditions, an exact replacement);
- the GPU path (an exclusive cost breakdown, hot spots, a libgpu-level design);
- the Media Engine for the SPU (feasibility, and PPSSPP's support for it).

Their reports go to `D:\Temp\PSX2PSP-Reborn\research\`. What they find is checked in the code
before it is used.

## 2. Order of the work, by measured cost

Each step ends with a bench line against the same snapshot, and with compare mode where pixels
are concerned.

1. **Timer polling**: the reads that wait for a counter value become a jump of PS1 time to the
   value (HLE of the wait, exact semantics: the counter the game measures with must give the
   same results).
2. **GPU packets → GE**: the ordering-table walk and the common GP0 primitives straight into the
   GE list, with no per-word device emulation (libgpu level, as RecompOne does its LibGpu).
3. **SPU**: the voices that are off cost nothing; then the mixing on the Media Engine if PPSSPP
   runs it, with a main-CPU path where it does not.
4. **Disc**: an asynchronous read-ahead thread, so inflating a block never stalls the guest.
5. **Recipes**: hooks by address or signature for library functions that are cheaper on the host.
6. **CPU shift**: once the host has headroom, the game gets more PS1 cycles per frame
   (`cpu_shift`), up to a locked 60.

## 3. Step 1 done: libpad's timer waits as recipes

Two waits on root counter 2 in libpad drove the timer cost (~76k reads, 121 ms per second in a
level): `_padChkRC2wait` (polled by `_padSioRW2` and its callers) and the /ACK loop inside
`_padSioRW2`. Both are now recipes (`crates/psx2psp-recomp/src/hooks.rs`): found by their exact
words with link-time immediates masked, checked on their `j` targets and globals, and replaced by
one host call (`pc | HOOK`, id, two arguments). The runtime (`psp/psxrt/native.c`, "recipes")
reads the same registers, gives the guest the same `v0`/`v1`/`a0`, and when the wait has not
ended lets PS1 time jump to its expiry or to the next device event, whichever comes first; an
/ACK or an IRQ ends it as on the PS1. An id the runtime does not know falls back to the
interpreter, so an older runtime stays correct.

Bench, 15 s from the same level snapshot (frame 7000, PAL60):

| | before | recipes |
|---|---|---|
| game fps | 25.8 | 43.6 |
| io ms/s (timer) | 337 (121) | 218 (12) |
| update ms/s | 159 | 147 |
| sleep ms/s | 124 | 254 |

The pad still drives the menus (the scripted run reaches the level and the snapshot is taken),
661 recipes run per second. With a quarter of the second idle, the next costs are draw (115),
SPU (115) and DMA2 (142): steps 2 and 3.

## 4. Steps 2 and 3, and the GTE

- **SPU**: halfword reads and writes of SPU RAM are single loads and stores; a voice that is off
  clears its output only when the next voice modulates from it or it is captured; the reverb
  takes its work-area view (base, size, position, write enable) once per step instead of per tap.
- **GPU packets**: a DMA2 linked-list packet goes to `gpu_gp0_packet` whole, so the common GP0
  commands are decoded from PS1 RAM without one device write per word.
- **GE**: a texture page or CLUT is sent again only when a tile it covers changed since it was
  last checked (`nver`, `rk_*`), and the newer-tile marks are kept as one rectangle until the next
  readback.
- **GTE door**: translated `COP2` commands call `GTE_CMD` (`psxrt_gte_cmd`), which saves only
  at, v0, a0, gp, sp, ra and HI/LO and calls `native_gte_fast` (`psp/psxrt/gte_fast.c`). That
  file is `core/gte.c` built with v1, a1-a3 and t0-t9 callee-saved, plus fast paths for NCLIP,
  AVSZ3/4 and RTPS/RTPT (in range: no divide overflow, no saturation).
  - It must be built with `-fno-optimize-sibling-calls`: a sibling call's epilogue restores
    a1-a3 over the arguments just set, so `op_avsz`, `op_rtp` and `gte_command_cs` received the
    caller's a1 as the command. `gfcheck.sh` now fails the build check on any sibling call.
  - The fast paths match `core/gte.c` on 5,000,000 random commands (MSVC differential test), and
    the sim's output with them is bit-identical to the reference.
- **GTE time** (`psxrt.trace` bit 7, `psxrt_gte_prof`: one command in 16 timed, less the cost of
  an empty timed interval): ~250k commands and 350-380 ms per second of a level. The GTE is now
  the largest single cost; next is emitting NCLIP/AVSZ inline in the recompiler and entering the
  other commands by opcode, without the door's dispatch.

Bench from the same level snapshot (PAL60; step 1 over 15 s, now over 10 s with `cpu_shift` 1):

| | step 1 | now |
|---|---|---|
| speed | - | 95% |
| game fps | 43.6 | 55.5 |
| io ms/s (draw, SPU) | 218 | 233 (182, 72) |
| DMA2 ms/s | 142 | 193 |
| update ms/s | 147 | 123 |
| sleep ms/s | 254 | 37 |

The game runs ~27% more frames per second in the same wall time, so per-frame costs fell more
than the per-second figures show. Compare mode on the snapshot gives the same differing pixels
as the previous runtime (~48k per second, mostly one step: the GE does not dither).
