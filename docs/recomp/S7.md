# S7: release work brought forward

## Memory card (S7a)

Sheep Dog checks the card before its main menu, so gameplay is unreachable without one; the
card comes before the remaining S4c and S5 work.

- **Level:** the BIOS, not the SIO port. libcard's primitives (`_card_info`, `_card_load`,
  `_card_read`, `_card_write`, `_new_card`), the card file API on "bu00:"/"bu10:" (open with
  create, read, write, lseek, close, firstfile/nextfile, erase, format) are answered in
  `core/card.c` on a 128 KB image in Sony's layout, interchangeable with other emulators' .mcr.
- **Completion:** at once. The HwCARD/SwCARD events (IOE, or TIMEOUT for an empty slot) are
  delivered before the call returns; an async file operation returns 0 and raises them, a
  synchronous one returns the byte count.
- **Host:** slot 0 is `card0.mcr` beside the EBOOT, created formatted when missing; slot 1 is
  empty. The image is written back 30 frames after the last change and at exit.
- **Device table:** libapi's `firstfile` looks the device up by name in the kernel's DCB table
  (0x150/0x154) before calling B(42), and points the entry at its own fix. Without the table it
  returned "no file" without asking the BIOS: the game's own save was never found. The BIOS
  now lists "cdrom", "bu" and "tty"; B(42) is still answered by the HLE.
- **Result:** the card check passes; the game creates its save file (1 block, a valid "SC"
  header), and at the next boot finds it and offers Load / New game with automatic save on.
  The intro scene runs at 100% speed, ~40k polygons/s. The save made at the end of a level is
  tested under "Later levels (S7d)".

## Test harness

- **Scripted pad:** `psxrt.pad` beside the EBOOT, lines of "frame buttons(hex) frames", ORed
  into the pad state; up to 256 presses. Reaches gameplay without a person at the keyboard.
- **Shots:** `psxrt.shots` lists frame numbers; at each one the displayed area is read back
  from VRAM and written as `shotNNNNN.bmp` (24-bit, 15-bit and 24-bit modes). It replaces
  host screenshots, which need an unlocked desktop.
- **RAM dumps:** an "rN" entry in `psxrt.shots` writes the 2 MB of PS1 RAM at frame N as
  `ramNNNNN.bin`, for disassembling code loaded at run time.
- **BIOS log:** an unimplemented BIOS function is logged once, not at every call; card opens,
  formats and erases are logged.
- **RAM pokes:** `psxrt.poke` beside the EBOOT, lines of "from to addr(hex) bytes(hex)", up to
  16 lines of up to 32 bytes; the bytes are written at every vblank from frame `from` to `to`,
  like a cheat code. The simulator takes the same pokes as `--poke FRAME:ADDR:HEX,...`, and
  `--dump FRAME,...` writes RAM as `ramNNNNN.bin`. Nothing in the runtime knows the game.

## Later levels (S7d)

- **How they are reached:** the game passes the next executable's path between executables in
  RAM at 0x80010000 ("\LEVELS\<NAME>\<NAME>"). A poke that writes another level's name there
  while the menu hands over to level 1 (frames 3000-3600 of `level.pad`) makes the game load that
  level instead. This was worked out in the simulator first, then run in PPSSPP.
- **Results in PPSSPP** (frame 7000, about 80 s into the level):

| Poke | Executable loaded | Speed | Picture |
|---|---|---|---|
| LEV05 | LEV05.EXE, 5.3 MB of native code | 99-100%, 49 fps | level drawn, Ralph standing |
| LEV09 | LEV10.EXE, 4.8 MB of native code | 99-100%, 49 fps | level drawn, Ralph standing |
| LEV17 | LEV17.EXE, 3.8 MB of native code | 99-100%, 49 fps | final level drawn, Marvin present |

- **LEV09 loaded LEV10.EXE:** the game picked the executable itself after the poke; the poke
  only names the folder. Not looked into further.
- **Not tested:** the levels reached by playing rather than by poke.

### End of a level and its save

- **How a level ends:** read from LEV00's code. A level keeps a flags word in its data (in
  LEV00 and LEV01, 0x800B037C). Bit 0 set means "leave the level"; with no other bit set, the
  exit handler (0x800341B4) calls the level-end function (0x80085730) with "won". That
  function marks the level in the handoff block (0x90 = level, 0x6C = furthest level) and
  names the next module in byte 0x8E: -3 SCENE (the TV studio), -4 FEND after level 16,
  -5 ENDING after level 17.
- **Who saves:** only FEND, SCENE (byte-identical to FEND) and WHEEL contain the card code;
  the levels do not. SCENE's save function (0x800650A0) erases the old file (B(45)), creates a
  new one (open with 0x10200), and writes 0x200 bytes with a checksum.
- **Test in PPSSPP:** one poke, `6000 6000 b037c 01000000`, while level 1 runs. The level ends,
  SCENE plays the after-level sequence (the sheep counter drops from 17 to 16, then "Activate
  it, and win a bonus point!"), and the log shows the card sequence: two reads, B(45) erase, an
  open that fails (the file is gone), create, write, then "card saved". 27 bytes of the card
  change: the progress record and its checksum.
- **Reload:** at the next boot, with no poke, the game reads the card and offers "Load game:
  automatic save on. Game 1: 16 sheep to catch, 0 bonus". Loading goes straight to the studio.

## GUI Native mode (S7b)

- **The switch:** the Build card has a RUNTIME switch, POPS (the default) or Native, with a hover
  note on each. Native calls `engine::convert_native`, the same path as the CLI's `--native`.
- **Checks before work starts:** Native refuses more than one disc with a toast that points to
  POPS. A game's POPS `min_level` is not applied, since POPS is not involved.
- **Tests:**
  - `native_takes_one_disc`: two discs give the toast and no job.
  - `native_build_writes_eboot` (ignored, needs `PSX2PSP_NATIVE_CUE`): the GUI's build function
    writes a valid PBP from the Sheep Dog disc in 3.8 s (release).

## Frame rate (S7c)

- **Measured in PPSSPP, 809 s:** the run uses `move.pad` and stays in level 1 for 702 s. The
  runtime logs, once a second, the emulated time against wall time (%) and the frames shown.
- **The target is the game's own rate:** a PAL PS1 frame is 314 lines of 2168 cycles, so
  49.75 Hz. The PLAN's "60 fps" is the NTSC case. A frame is shown at every emulated vblank,
  and the game is not sped up.

| Section | Seconds | fps (mean, min-max) | Seconds under 49 fps | Sleep |
|---|---|---|---|---|
| Boot and intro | 30 | 48.9, 46-51 | 6 | |
| FMV and menus | 86 | 48.6, 38-51 | 11 | |
| Level 1 | 702 | 49.0, 48-50 | 2 (48 fps) | 190-560 ms/s, mean 258 |

- **Level 1 is locked:** 699 of 702 seconds run at 99-100% (49 fps shown, since the counter
  rounds 49.75 down). There is about 25% of the CPU to spare.
- **Where it drops:** four of the five worst seconds (77-84%) are the seconds in which a level
  overlay is read from DATA.PSAR. The read blocks, the code is then native. The fifth (89%, at
  frame 5526) is a busy scene with 148 ms of drawing.
- **Not measured:** frame-to-frame pacing inside a second. The PSP shows 49.75 Hz frames on a
  59.94 Hz panel, so some frames stay up for two refreshes. That is inherent to PAL on the PSP.

### The TV studio (S7e)

- **Measured in PPSSPP:** the SCENE route of the harness (a poke names SCENE while the menu
  hands over), 110 s from 100 frames after SCENE.EXE loads to frame 9000. It had the lowest
  speed of the modules tried: 91.5% mean and ~16 audio gaps a second.
- **Where the time went:** two general costs, found with the runtime's profile counters.
  - **Timer reads:** the game reads the root counters tens of thousands of times a second, and
    every read divided a 64-bit cycle count, a library call (`__udivdi3`) on the Allegrex. The
    cycles per tick are now a 32-bit 16.16 value and the division is 32-bit whenever the
    elapsed cycles fit. The simulator gives bit-identical results to the previous code.
  - **CLUT conversions:** the studio draws models interleaved in depth order, each with its own
    CLUT, so the single cached CLUT was converted again 5.5k times a second. The cache now holds
    32 CLUTs, slotted by a hash of the key. A texture page also remembers the VRAM epoch at
    which its stamp was last checked, and skips the check while nothing wrote VRAM.
- **Result:** 97.9% mean (min 87, 10 s under 95), 3.9 audio gaps a second, ~525 CLUT
  conversions a second. The picture at frame 7000 is byte-identical to the one before the CLUT
  cache.
- **What is left:**
  - **Whole-VRAM readbacks:** ~11 a second, ~55 ms a second. The studio copies areas the GE drew
    within VRAM, so VRAM comes back to RAM first; PPSSPP charges a readback by its size.
  - **Partial readbacks crash PPSSPP 1.19.3:** a readback of only the needed rows (full-width
    strips) took 16 ms instead of ~250 ms for 50 readbacks, but PPSSPP crashed (access violation
    in PPSSPPWindows64.exe) within 3300 frames. The runtime keeps the whole readback; the strip
    readback is a lead for real hardware only.
  - **Drawing:** the GPU DMA list costs ~300 ms a second for ~50k polygons.
  - **Worst seconds (87%):** scene changes in the studio.

### Open items

- **Blocking overlay reads (kept):** the native code of an executable (0.4-5.3 MB) is read from
  DATA.PSAR and inflated at the game's `Exec`, after the game has read the executable from the
  disc and before its first frame. Emulated time stops meanwhile: one second at 77-84%, so
  ~160-230 ms, once per module change, on a load or black screen. Reading it in the background
  during the game's own disc read would hide it, but the executable is known only once its
  whole text is in RAM, and its host area is the one the previous module's code occupies. Not
  worth the risk for a pause inside a load.
- **Merge into master:** `recomp` is 42 commits ahead of master and master has one commit
  (`media/framing`) not in `recomp`; the merge has no conflicts. Native is off by default (POPS stays the default runtime).
