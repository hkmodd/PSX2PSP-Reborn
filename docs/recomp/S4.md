# S4: PS1 drawing on the GE

Measured at the language wheel (S3 8/n, 53ad069): the software rasterizer takes ~800 ms per
second of guest time for ~4.5k primitives and ~1.2M fragments (0.69 us per fragment). No CPU
path reaches full speed at 250-375k fragments per PS1 frame, so the GE draws.

The GE facts below come from PPSSPP's software renderer (hardware-probed comments) and pspsdk,
collected in `GE_FACTS.md` (research notes, outside the repository). PPSSPP's hardware renderer
is the oracle we run, so where it differs from the GE it decides what we may rely on.

## Why S0 decision 6 changes

S0 put PS1 VRAM in PSP VRAM and had the GE read textures and CLUTs from it. Two facts rule that out:

1. **The GE cannot sample PS1 texture pages in place.** A PS1 VRAM row is 2048 bytes: 2048 T8
   texels or 4096 T4 texels. The maximum TBW is 2032 for T8 and 2016 for T4.
2. **The oracle cannot either.** For a 5551 framebuffer, PPSSPP's `CanDepalettizeBufferAs`
   rejects CLUT4. It also takes a CLUT from a rendered framebuffer only from its first row; any
   other CLUT is read from stale RAM.

So there are **two copies** of PS1 VRAM:

- **`Gpu.vram` in RAM** is the CPU's copy, as in S3. Transfers, texture sources, CLUTs and the
  software fallback all use it.
- **PSP VRAM** is the GE's copy, and the GE draws there.

The core tells the renderer what it reads and writes (`GpuRenderer` in psx.h). The renderer
keeps the two copies in step with GE block transfers, which PPSSPP turns into framebuffer
uploads and readbacks (`NotifyBlockTransferBefore/After`).

## PSP VRAM layout (2 MB)

| Offset | Size | Content |
|---|---|---|
| 0x000000 | 1 MB | PS1 VRAM, 5551, FBW 1024: the GE's draw buffer (region/scissor up to 1023x511) |
| 0x100000 | 0x44000 | display buffer A, 565, 512x272 |
| 0x144000 | 0x44000 | display buffer B |
| 0x188000 | 480 KB | free |

- 5551 is the PS1 pixel: R 0-4, G 5-9, B 10-14. Bit 15 is the GE stencil and the PS1 mask bit.
- At 0x04000000, PPSSPP takes the PS1 VRAM as one 1024x512 framebuffer. It matches texture reads
  at any Y offset inside it below 0x04110000, and that is how the display is shown.
- The renderer clears the whole buffer with the GE before the first upload, so the oracle has a
  framebuffer to upload into.

## Coherence: 64x32 tiles

- **`ge_newer` bit per tile.** It means the GE's copy is newer than RAM. A GE draw sets the bits
  under its clipped bounding box.
- **`read(rect)`:**
  1. Wraps the rectangle around VRAM and looks for a `ge_newer` tile under it.
  2. If there is one: writeback-invalidates the data cache and block-transfers **all** of PS1
     VRAM to RAM. The oracle reads back pieces of a framebuffer this large wrongly, and the GE's
     copy is never behind RAM's, so the tiles nobody asked for come back unchanged.
  3. Waits for the GE, clears every bit, and bumps the generation of the tiles that were newer.
- **`wrote(rect)`:** writes back the data cache and draws the rectangle as a 5551 textured sprite
  from RAM, in pieces at most 512 texels wide. It bumps the generation and leaves the bits alone:
  the rest of the tile may still be newer in VRAM.
  - The oracle turns a RAM->VRAM block transfer into a lossy redraw; a sprite is exact on both.
  - Two passes keep bit 15: every pixel with stencil ZERO, then alpha GREATER 0 with stencil
    REPLACE.
  - Before the real `TexImage`, a dummy one at another address: the oracle rehashes a RAM
    texture only when the address register changes, so a second upload from the same place would
    draw the first one's pixels.
- **`ge_touch`, once per presented frame:** a 1x1 sprite with pixel mask 0xFFFFFFFF (writes
  nothing) and the scissor set to the whole 1024x512. The oracle drops a framebuffer that has not
  been drawn for a few frames, together with what the GE drew there, and sizes it by the scissor.
- **Who calls them.** The core calls `read`/`wrote` around:
  - transfers;
  - copies and fills it draws itself;
  - every primitive the renderer leaves to software.

  The renderer itself calls `read` before it builds a texture or CLUT from RAM. A game that
  renders to a texture therefore gets a readback, which is slow in PPSSPP but correct.

## Primitives

- **Through mode, float vertices shifted by +0.5 px.**
  - The GE samples pixel centres; PS1 samples integer corners.
  - The shifted GE triangle T+0.5 contains the centre x+0.5 exactly when T contains x.
  - Both use the top-left rule.
  - UVs get +0.5 as well: the GE floors at the centre, while the PS1 (our rasterizer) rounds.
  - 8-bit colours stay floored (±1 in 8 bits).
- **Negative coordinates.** The GE's handling of negative through-mode coordinates is unknown.
  A polygon with a vertex left of or above PS1 x/y = −0.25 is clipped there on the CPU
  (Sutherland-Hodgman, attributes interpolated). Visible pixels start at 0, 0.75 px away, so
  rounding the new vertices to 1/16 cannot reach them.
- **Rectangles** are GU_SPRITES with integer s16 corners, which cover exactly [x, x+w). Flipped
  rectangles start their UV one texel further.
- **Lines** stay in software (the PS1 line walk differs from the GE's); they are counted.
- **Drawing area:** the GE scissor. **Drawing offset:** added by the core.
- **Bit 15 / mask.** The stencil test is always on, with ref 0xFF and pixel mask 0:
  - func: NOTEQUAL when the mask check is on (passes when bit 15 = 0), else ALWAYS;
  - zpass: REPLACE when the written bit is 1, else ZERO.
- **Semi-transparency:** blend FIX factors, exact on the GE except B+F/4:

  | PS1 mode | GE blend |
  |---|---|
  | B/2+F/2 | ADD, FIX 0x7D7D7D both |
  | B+F | ADD, FIX 0xFFFFFF both |
  | B−F | REVERSE_SUBTRACT, FIX 0xFFFFFF both |
  | B+F/4 | ADD, src FIX 0x3A3A3A, dst FIX 0xFFFFFF (best FIX, 832 of 1024) |

- **Dithering:** the PS1 matrix in `sceGuSetDither`, enabled per primitive. It applies after
  blending, as on the PS1. The oracle ignores it.
- **Fill:** a flat sprite with scissor = the fill rectangle, split where it wraps. No dither, no
  blend; stencil ALWAYS/ZERO, since fill ignores the mask and clears bit 15.
- **Copy:** software. The oracle does not carry out a VRAM->VRAM block transfer inside one
  framebuffer (the destination keeps its old pixels). The source is rarely a place the GE drew,
  so a copy costs one upload of the destination.

## Textures

- **CLUT pages (4/8 bpp).** The page's rows are copied from RAM into a compact T4/T8 256x256
  texture: 128 or 256 bytes a row. The low nibble is the even texel on both machines.
- **CLUTs** are converted to 8888 with the alpha carrying what the texel means:

  | Texel | Alpha |
  |---|---|
  | 0x0000 | 0x00 (transparent) |
  | STP bit set | 0x80 (semi) |
  | otherwise | 0xFF (opaque) |

- **15-bit pages** are converted to 8888 with the same alpha encoding.
- **Cache.** Slots in RAM, keyed by page/CLUT and validated by the generations of their tiles. A
  slot used since the last GE sync is not evicted. Every fill is followed by
  `sceKernelDcacheWritebackRange`, which PPSSPP also takes as a texture invalidation.
- **Passes, chosen from the CLUT's flags (has opaque, has semi):**
  - **Opaque primitive:** alpha GREATER 0. Bit 15 is per texel, so where a CLUT mixes STP values
    it takes two passes: alpha 0xFF, then alpha 0x80.
  - **Semi primitive:**
    1. alpha EQUAL 0xFF, no blending;
    2. alpha EQUAL 0x80, blended, bit 15 = 1.
- **Modulation:**
  - **Textured:** MODULATE with colour doubling, prim = c−1. 0x7F is exactly 1.0 on the GE, the
    same as PS1 0x80.
  - **Raw:** REPLACE without doubling.
  - The vertex alpha is 0xFF, so the alpha test sees the texel's alpha.
- **Texture window** (E2 mask ≠ 0): software for now, counted.

## Batching and sync

- **One display list, kicked as it grows.** It is a GU_DIRECT list: libgu moves the stall address
  at each draw.
- **The list flushes and waits:**
  - when `read` finds a `ge_newer` tile;
  - when the cache must evict a slot in use;
  - when the list is nearly full;
  - when presenting.
- **Presentation:**
  - The PS1 display area is drawn into the 565 display buffer as a sprite. The sprite is textured
    from the GE's PS1 VRAM: 5551, TBW 1024, base at the display row.
  - The 24-bit (MDEC) mode first calls `read` on the display area, then converts from RAM as in S3.

## Test

- **Compare mode:** bit 3 of `psxrt.trace`.
  - The renderer returns `GPU_BOTH`, so the GE and the software rasterizer each draw every
    primitive.
  - Once per second the GE's copy is read back whole and compared with RAM. The log prints
    `-- ge: diff N px` with the bounding box.
  - The oracle's renderer is not bit-exact (no dither, host blending and rounding), so the
    target is a small diff count, not zero.
- **Per-second log line:** primitives drawn on the GE, primitives left to software (by reason),
  readbacks, uploads and flushes.
- **All software:** bit 4 of `psxrt.trace` installs no renderer, for A/B runs.

## What the oracle does (PPSSPP 1.19.3, read as reference only)

| Behaviour | Consequence here |
|---|---|
| A framebuffer not drawn for 6 flips is decimated, with its pixels | `ge_touch` every frame |
| A framebuffer is sized by the scissor of the draws into it | `ge_touch` uses the full 1024x512 scissor |
| Reading back part of a 1024x512 framebuffer returns wrong pixels | `read` brings back the whole of VRAM |
| A RAM->VRAM block transfer is a lossy redraw | uploads are textured sprites |
| A VRAM->VRAM block transfer inside one framebuffer does not land | copies stay in software |
| A RAM texture is rehashed only when TEXADDR/TBW/format changes, at flip, or on an invalidate over the current address | a dummy `TexImage` before every upload |
| The hardware backend does not dither | 1-step differences in compare mode |

## S4a results (Sheep Dog, gameplay)

- **Compare mode**, after the copy fix: ~53k differing pixels per second out of 512k. Almost all
  differ by one step (no dither in the oracle); ~900 differ by more, on the edges of tiny additive
  triangles, where the oracle's coverage rule differs. No region is wrong.
- **Normal mode** is stable from boot to gameplay.
- **Speed:** FMV 4 fps, loading 2-5 fps, gameplay 2 fps (4 fps in compare mode, which never reads
  back). Per second of gameplay: ~3000 GE triangles, ~1900 textured primitives in software and
  ~176 whole readbacks, draw 1.6 s. Each textured primitive in software reads a texture page from
  RAM after the GE drew, so it costs a whole readback: the GE and RAM ping-pong. S4b removes it.
