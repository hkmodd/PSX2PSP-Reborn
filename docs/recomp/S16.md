# S16: the GE fed during the frame, measured on the real PSP

The first real-PSP log of S15 (`docs/recomp/S15.md` build, PAL60, `cpu_shift` 0) disagreed with
PPSSPP everywhere the GE was involved:

| | PPSSPP | PSP |
|---|---|---|
| intro (MDEC, 24-bit) | 100%, present 16 ms/s | 52%, 31 vbl, 7 fps, present ~525 ms/s |
| level 1 | 100%, present ~13 ms/s | 54-58%, 33 vbl, 24 fps, present 190-230 ms/s |
| menu, 62 polygons a frame | 100% | 100%, present ~350 ms/s |

`present()` ends with `ge_sync()`, so its time is the GE's work that the CPU waited for. The
`-- ge:` lines said why it waited: **kick 24** a second at 24 fps, one stall move a frame.

## 1. The stall moves every 1 KB

`ge_kick` moved the list's stall address every `STALL_STEP` = 16 KB. A frame of level 1 is
about 20 KB of list, so the GE got its first 16 KB late in the frame and the rest at
`present()`. The CPU and the GE took turns instead of working together.

`STALL_STEP` is now 1 KB, about 60 polygons. In level 1 that is ~15 kicks a frame, a few hundred
`sceGeListUpdateStallAddr` calls a second. `ge_kick` also reads the list's size inline instead of
calling `sceGuCheckList` once per polygon.

## 2. The 24-bit conversion only when the picture changed

S15's GE conversion (`ge24`: 960 one-pixel columns, CLUT byte selection and pixel masks) ran at
every vblank. A movie changes its picture at ~15 fps. `gpu_writes` (core/gpu.c) counts every
draw, copy, fill and transfer into VRAM. `ge24` now redoes the conversion only when this count,
the display position or the size changed, and at least once a second.

In PPSSPP the intro's present draw time went from 8 to 2-3 ms/s. The frame 60 and frame 600
checks still compare the GE's picture to the CPU's: 0 of 81920 pixels differ. The real PSP's S15
log had 0 differences too: the GE conversion is exact on the hardware.

## 3. The vertex ring through the cache, A/B on the device

The fast lane wrote its vertices through the uncached mirror: about 30 uncached stores per
polygon. The ring can now also be written through the cache, with
`sceKernelDcacheWritebackRange` over the new bytes (`ring_flush`) before every stall move and
before `sceGuFinish`'s.

The GE only reads vertices that list words before the stall point to, so it never sees a
vertex that is not yet in RAM. Switching modes happens in `ge_sync`, when the GE is idle, with a
writeback-invalidate of the whole ring:

- a line left dirty by the cached mode would otherwise be written back over later uncached
  stores;
- a line left clean but stale would otherwise be written back together with new cached stores.

PPSSPP has no data cache, so it cannot tell which mode is faster. The runtime alternates the
modes every second (`ring_ab`), and each `-- ge:` line ends with `ring cached|uncached (wb N ms)`.
The `-- gpu: poly n/ms` line of the same second gives the cost per polygon in each mode.

## 4. Figures only the device has

- **Boot microbenchmark.** `ge: 64 KB of vertices in A us uncached, B us cached and written back`.
  It writes the same vertices as `rd_poly`. PPSSPP reads 213 / 214 us.
- **Present split.** `present N (wait W draw D text T rgb24 R)`:
  - W: the GE still drawing the frame when `present()` starts;
  - D: `present()`'s own list (the 24-bit conversion, and the PS1 picture to the screen);
  - T: the debug text.

  In PPSSPP the level reads `present 13 (wait 3 draw 1 text 8)`.

## 5. Checked

- **Compare mode** from `level1.snap`, 10 s, against the software rasterizer. The difference
  counts are the same as before S16 (45-53k pixels a second, mostly 1-step dither and colour
  rounding), and the same in cached and uncached seconds.
- **Level 1 bench** (PPSSPP): 100%, 59 vbl / 59 fps.
- **Intro bench** (PPSSPP): 100%, 14.1 fps, as in S15.

The real-PSP figures for each change come from the next device run.
