# S15: MDEC on the VFPU, and 24-bit movies converted by the GE

The first real-PSP run (S14) played the intro FMV at 28% speed. PPSSPP had it at 100% with
`mdec` at 242 ms/s, and on top of that `present` spent ~90 ms/s:

- `ge_read` brought all of PS1 VRAM back to RAM every frame;
- `convert24` then turned it into an 8888 texture on the CPU (`rgb24` 80 ms/s).

The real PSP is much slower than PPSSPP at multiplies, float conversions and uncached reads, so
both costs are larger there.

## 1. MDEC colour macroblocks on the VFPU (`core/mdec.c`, `__psp__` only)

- **IDCT.** out = S^T B S is two 8x8 matrix products, each eight `vmmul.q` on 4x4 quadrants.
  - `lv.q` loads a column, so the row-major blocks arrive transposed. The registers compute the
    transpose, which the stores undo.
  - The factors are built once per scale table, quadrant-blocked. They are rebuilt when a new
    table arrives (`mdec_write` sets `vf_stale`) and differs from the last one.
  - The luma blocks' x is permuted to 0 2 4 6 1 3 5 7. An output row is then an even and an odd
    quad, each pairing with the same four chroma samples.
- **Colour.** The hardware's integers are held in floats: IDCT results rounded and clamped to a
  signed byte, chroma terms k/256, + 128.
  - `vf2iz` by 2^23 truncates and saturates.
  - `vi2uc` keeps bits 30-23 with negatives at 0, so the 0-255 clamp is free. On a matrix row it
    packs one pixel's R, G, B.
  - The 15-bit and 24-bit output (sign and bit 15 included) is packed from those words in C.
- **RLE.** `vf_rle` decodes straight into the VFPU's s32 coefficient blocks with one multiply per
  coefficient, `(n * qq + 4) / 8`. `qq` is the quant table times the block's scale, cached per
  table and scale.

Monochrome output (4- and 8-bit depths) keeps the C path. So does everything if the boot check fails.

### Checked at the first colour macroblock

- **Colour.** 64 random macroblocks (DC within +-500, ten AC values within +-64) go through the
  exact C IDCT and `yuv`, and through the VFPU, for each depth, sign and bit-15 setting. Each
  channel may differ by 1 at most.
- **RLE.** 512 random streams must give the same return value, position and coefficients as the C
  decoder:
  - some start with 0xFE00 padding;
  - some have q = 0;
  - some are cut short.

PPSSPP logs:

    mdec: VFPU IDCT and colour in use, 0 of 49152 channels differ by 1, 0 by more; 0 of 512 RLE blocks differ

## 2. 24-bit display converted by the GE (`main.c`, `ge24`)

With the renderer on, the movie frame is already in the GE's copy of PS1 VRAM. Pixel x's channel c
is byte b = d + 3x + c of its line, d being the line's offset past a 16-byte boundary.

- PS1 VRAM is read as a T16 index texture: halfword b >> 1, with CLUT shift 8 * (b & 1) picking
  the byte.
- A grey CLUT turns that byte into all three channels. The pixel mask then keeps only channel c.
- Every (c, s) pair is one draw of 1-pixel column sprites, for each x with (d + 3x + c) & 1 == s.
  That makes 6 draws and 3w columns into a 5650 buffer at VRAM 0x188000, free after the two display
  buffers.
- The scaled sprite then textures from that buffer, as before.

Nothing is read back and the CPU converts nothing. The vertices and the CLUT are built once per
size.

The CPU path stays for these cases:

- lines past 512 halfwords (the GE's widest texture), e.g. 24-bit 368 or 512 wide;
- lines that wrap at VRAM's right edge;
- heights over 256;
- the software renderer.

What PPSSPP emulates decided the texture format. These two attempts failed first:

| Attempt | PPSSPP |
|---|---|
| PS1 VRAM read as T32 (byte shift 0-24) | reads black: a 16-bit framebuffer is not reinterpreted as T32 |
| a GE copy of the lines to RAM first, then T32 from RAM | crashes PPSSPP 1.19.3 (access violation at +0x1b0efa), at random times |
| PS1 VRAM read as T16 (byte shift 0 or 8) | correct, no crash |

### Checked at run time

On the 60th and 600th frames the GE converts, `present` also reads the area back and converts it
on the CPU. The GE's buffer is copied to RAM (`sceGuCopyImage`) and compared bit for bit:

    rgb24 on the GE: 0 of 81920 pixels (0 not black) differ
    rgb24 on the GE: 0 of 81920 pixels (80816 not black) differ

If any pixel differs, the CPU path takes over for good and the log says so. A real PSP that
treated the pixel mask on a 5650 buffer differently would fall back on its own.

## 3. Measured (PPSSPP, intro from boot, PAL60, `cpu_shift` 1, 42 s)

| | before | VFPU MDEC | + GE 24-bit |
|---|---|---|---|
| mdec ms/s | ~242 | ~130-150 | ~130-150 |
| present ms/s | ~90 (rgb24 80) | ~85-90 | 16 (rgb24 0) |
| sleep ms/s (bench line) | | 478 | 535 |

Level 1 from `level1.snap` (10 s) is unchanged: 100%, 58.9 fps, sleep 241.

PPSSPP charges about one cycle per instruction. On the real PSP, the multiplies, divides and float
conversions the VFPU path removes, and the 1 MB uncached readback the GE path removes, cost more.
The next real-PSP `psxrt.log` will give the real numbers.
